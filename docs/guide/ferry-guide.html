Chapter 1 Everyone

The short version

If you read nothing else, read these five cards.

1

It moves customers into Temenos Digital

Ferry takes customer data from a bank's old system and creates the same customers in Temenos Digital: their contracts, accounts, users and approval groups.

2

It works with any old system

Nothing is built for one bank. Each bank's files are translated into one standard format by a small settings file, with no code change.

3

It checks everything first

Before anything is sent, Ferry finds every record that would fail and builds an exact, reviewable plan of every call it would make.

4

It works around open questions

Where Temenos or the bank has not answered yet, Ferry makes a named, switchable assumption and marks every record that relied on it.

5

Today it only prepares

The checking and planning half is built and tested. Sending to Temenos is the next step. Until then, nothing leaves the machine.

Chapter 2 Everyone

The problem we are solving

When a bank moves to Temenos Digital for online and mobile banking, every existing digital customer has to be recreated in the new platform. For a business customer that means far more than a name and a password.

Take a small company that banks online. In the new platform it needs a contract (its online-banking agreement), the customer numbers and accounts that belong to it, each person who logs in with their role, the groups that approve payments, the approval rules (who must approve what amount), limits and saved payees. Multiply that by thousands of customers.

Temenos provides a set of official web services for exactly this, called the DataMigration APIs: one call creates a contract, another links a user to it, another creates an approval group, and so on. Calling them is easy. Calling them well, at volume, is hard:

Every source is different

Each old system exports its own column names, codes and date formats. Spreadsheets also quietly drop leading zeros from customer and account numbers.

Bad data is expensive

A bad record found half-way through a live run leaves a customer half-built in the new platform, which someone then has to clean up.

Order matters

A user can only be added to a contract that exists. An approval group can only hold users that exist. Each step needs an ID that the previous step created.

Reruns must be safe

Runs will be repeated. The tool must remember what it already created, so a second run never creates a customer twice.

Some answers are missing

The vendor material leaves real questions open, such as how approval brackets should meet. We cannot wait for every answer before building.

Proof is required

At sign-off, the bank will ask what was migrated, what failed and why. Every item needs evidence, line by line.

An everyday comparison. Moving house with a professional mover: before the truck leaves, they label every box, check nothing is broken, and agree the order of unloading (furniture before the boxes that go inside it). They keep an inventory, so at the other end you can tick off what arrived. Ferry does the same for customer data.

Chapter 4 Everyone

Words you will meet

A handful of banking and tool terms carry the rest of this guide. Here they are, with one picture of how they fit together.

Contract

A customer's online-banking agreement in Temenos Digital. The unit of work in Ferry: everything else hangs off it.

CIF

Customer Information File number: the bank's ID for a customer in the core system, e.g. 045000100. Leading zeros matter.

Service definition

The package a contract gets (for example retail or business), which decides the features and permissions available.

Role

What a user may do: administrator, accountant, standard user. Each maps to a role ID configured in Temenos.

Linked user

A user who is also a bank customer with their own CIF. Temenos fetches their details from the core banking system.

Virtual user

A user with no CIF of their own, such as a company's accountant. Temenos needs all their personal details supplied.

Signatory group

A named team of users who approve payments together, used by business customers' approval rules.

Legal entity

The bank entity the contract belongs to. Usually one default per environment.

Batch

One set of source files that travel together through Ferry, e.g. "Retail mock run 1".

Canonical model

Ferry's one standard format for contracts, accounts, users and groups. Every source system is translated into it.

Mapping profile

A small settings file that tells Ferry how one source system's columns and codes translate into the standard format.

Finding

A problem found by a check. An error stops the record. A warning is only reported.

Voyage

The plan for one contract: the ordered list of calls Ferry will make to create it and everything under it.

Dry run

Working out exactly what would be sent, without sending anything. Everything Ferry does today is a dry run.

Assumption

A named, switchable decision (A-01 to A-12) Ferry makes where Temenos or the bank has not answered a question yet.

ID register

Ferry's memory: which old ID became which new Temenos ID, per environment. It stops a rerun from creating anything twice.

Chapter 6 Everyone

Boarding, step by step

Boarding is one screen with four steps, top to bottom. A progress bar at the top shows where the current batch stands.

Step 1 · Create a batch

A batch is a container for one set of files that belong together, such as "Retail mock run 1". You give it a name and, optionally, the name of the source system (for example LEGACYCORE). The source system tells Ferry which translation rules to use for that batch's files.

Batches are kept, so you can switch between them, compare runs, and come back later.

Step 2 · Load files

You load Excel or CSV files: one workbook with a sheet per record type (Contracts, Accounts, Users, Signatory Groups), or one file per type. Ferry offers a ready-made template workbook with the right column names and a sheet of instructions.

Two details make this step trustworthy:

  • Every value is read as text. Spreadsheets love to turn 001000111 into 1000111. Ferry reads exactly what the cell shows, so customer and account numbers keep their leading zeros.
  • Other systems' files are translated, not rewritten by hand. If the bank's export uses its own column names and codes, a mapping profile translates them on the way in.

How file reading and mapping work Technical

SheetReader reads .xlsx, .xls and .csv with Apache POI and Commons CSV, always through a DataFormatter, so each cell is taken exactly as displayed. Byte-order marks are dropped; non-breaking spaces become plain spaces. Sheets named Instructions, Readme or Notes are skipped; an empty sheet is skipped rather than failing the workbook.

MappingService resolves each source column in order: an explicit entry in the profile's columns, then the template label (the trailing * on required headers is ignored), then the canonical field name. It then applies transforms (trim, upper, lower, digits, list, date:<pattern>), then valueMaps, then defaults. Profiles are read fresh from config/mapping-profiles on every upload, so an edit applies without a restart.

Profile choice on upload: an explicitly chosen profile wins; otherwise the batch's source system plus the record type picks one automatically; otherwise template headers are assumed. Loading a record type again replaces that type in the batch and sends the batch back to "staged", so findings and plan always match the data.

Step 3 · Validate

Validation is where Ferry earns its keep. Every record passes through three layers of checks. Anything that fails becomes a finding, with the row, the field and a plain explanation.

Step 4 · Plan (the dry run)

For every contract, Ferry works out the exact list of calls Crossing will make, in order, with the exact message each call would send. We call this list a voyage.

The order follows the dependencies: the contract first, then its users, then the signatory groups made of those users. Later steps need IDs that only exist once an earlier step has run, so the plan holds a placeholder such as {{CONTRACT:B-100.contractId}}. Crossing will fill it in with the real ID Temenos returns.

Each voyage ends with one of three statuses:

  • ready every step can run, or was already done in an earlier run.
  • partial the contract can be created, but some users or groups cannot.
  • blocked the contract itself cannot be created, so nothing under it can either.

Steps also carry the assumption tags they relied on, so a reviewer can see at a glance which parts depend on open questions.

How the plan is built Technical

PlanService builds one voyage per contract from valid records only, and refuses to plan until the batch has been validated. Step IDs are contract, user:<ref> and group:<ref>; each step lists dependsOn, its assumptions, any reasons it is blocked, and its payload.

  • Contract step → CreateContract: legalEntityId (row or environment default), serviceDefinitionId (from reference data), primaryCif, and cifList and communicationDetails as JSON strings inside the JSON body, as the vendor guide requires.
  • User steps → LinkUserToContract for linked users (by CIF) or CreateVirtualUser for virtual users, chosen per record under A-01. The accounts list defaults to every account on the contract.
  • Group steps → CreateSignatoryGroup, with signatories holding {{USER:<ref>.userId}} placeholders.

Before marking a step planned, the planner looks in the ID register for this environment. If the item is there, the step becomes already done with the registered target ID, and it will not be sent again. The test aContractAlreadyInTheRegisterIsNotPlannedAgain covers this.

Approval mode, approval rules, limits and payees are designed (assumptions A-02 to A-06 already exist for them) and arrive in build steps 5 and 6.

Chapter 8 Everyone

Working without all the answers

Some questions about the Temenos APIs could not be answered yet by Temenos or the bank. Instead of waiting, or guessing silently in the code, Ferry keeps an assumptions register.

Each open question gets an ID (A-01 to A-12), the evidence from the vendor material, a sensible default, and the alternatives. The choice can be switched in Settings, and every switch is recorded with the person's name. Most importantly, every record and plan step that relied on an assumption is tagged with it, so when the answer arrives we know exactly what to re-check.

A-01Can Temenos read a user's details from the core, so a user can be linked by CIF?Per record: linked when the source gives the user a CIF, otherwise virtualAlways virtual
A-02In approval rules, is each group number a yes/no flag or a count of approvals?Yes/no flag per group; "two from the same group" rules are parkedCount per group
A-03Do neighbouring amount brackets share the boundary value?Shared boundary, as in the vendor examplesNext starts at previous + 1
A-04How should an amount range that needs no approval be sent?Not sentSend as NO_APPROVAL
A-05How do "all transactions" rules become calls?One call per action in the list set for the service definition—
A-06Rules for actions that move no money?Parked for reviewSend with configured limit type
A-07What if a contract name already exists (vendor error 10401)?Reported as its own outcome, never retried automatically—
A-08A virtual user is missing a field Temenos marks mandatory?Block the user until it is filledSend blank and flag

Chapter 9 Everyone

Safety by design

A migration tool can do real damage if it sends the wrong thing to the wrong place. Ferry is built so that the safe action is the default one.

Live calls are off

Each environment has a "live calls" switch, off by default. While it is off, nothing is sent. The top bar always says Safe mode or, in red, Live calls on.

Every run is confirmed

Even with live calls on, a run must be explicitly confirmed, against an environment that is always shown on screen.

Secrets are never stored

The Temenos app key and secret are typed in at run time and never written to disk or logs. Settings files hold no secrets.

Customer data stays local

Loaded files and results live in a local database folder that is excluded from Git, so customer data cannot be committed by accident.

Undo only what we made

Rollback will always preview first, and can only remove items found in Ferry's own ID register, never anything else in the target.

Everything is on record

Every run, setting change and assumption switch is recorded with who did it and when, in Settings → History.

The "200 OK" trap

Web services usually signal failure with an error status. The Temenos DataMigration services often do not: they can answer "200 OK" with a failure described inside the message. A naive tool would count that as a success. Ferry judges success only when opstatus is 0 and there is no error code (assumption A-10).

counted as success 
HTTP 200 OK
{ "opstatus": 0,
  "contractId": "1234567890" }
counted as failure 
HTTP 200 OK
{ "opstatus": 0,
  "dbpErrCode": "10401",
  "dbpErrMsg": "Contract name already exists" }

Example messages for illustration. The rule itself (which fields mean success or failure) lives in target-temenos.json.

Chapter 10 Everyone

The console: looks and room to grow

The console is the web page you use to drive Ferry. It follows the Avenza look: black navigation, orange highlights, clean type, in light or dark.

  • Left: the stages, grouped (Migration, Setup). Stages not built yet show their build step, e.g. "Step 3".
  • Top: where you are, the environment and its safety state, the light/dark/system switch, and your name (recorded on every change).
  • Phones and tablets: the navigation folds into a menu; nothing scrolls sideways.

It is also built to grow. Each stage is a self-contained module. Adding Crossing, Manifest or anything new (a rule converter, a reconciliation view) means adding one folder; the navigation, links and page frame appear automatically.

What the 15 tests prove Technical
  • The sample batch produces exactly the documented voyages (R-001 partial … R-004 blocked).
  • A contract already in the ID register is not planned again.
  • Loading files again sends a batch back to "staged", and planning is refused until it is re-validated.
  • The template workbook loads in one go; a legacy export maps through its profile.
  • Template headers match without a profile; unknown columns and missing required columns are named.
  • Profile columns, transforms, value maps and defaults apply in the right order.
  • CSV keeps leading zeros and drops the byte-order mark; workbooks keep text cells and skip instruction sheets.
  • Unknown settings keys are refused; note keys are kept; an unknown assumption option is refused.
  • The status call shows the target and that live calls are off.
  • The ID register skips duplicates and refuses a second target ID for the same item.
Chapter 12 Everyone

Try it yourself

Ferry runs on one laptop. It needs Java 17, Maven and Node.js installed. Then it is two commands and a browser.

1 · Start the server

mvn -f ferry-server/pom.xml spring-boot:run

2 · Start the console (second window)

npm --prefix ferry-console install   # first time only
npm --prefix ferry-console run dev

3 · Open the console

Go to http://localhost:5196 and type your name in the top-right box.

A five-minute walkthrough

  1. In Boarding, click Switch or create, name a batch, leave the source system blank, and create it.
  2. Under Load files, choose samples/excel/synthetic-batch.xlsx and click Load into batch.
  3. Click Validate. Read the findings by check, then every finding.
  4. Click Build plan. Open Calls on B-100 and then Request on a step.
  5. Repeat with clean-batch.xlsx (everything ready) and with legacycore-batch.xlsx in a batch whose source system is LEGACYCORE.
  6. Look through Settings: environment, assumptions, reference data, history.
Nothing you do here reaches Temenos. Live calls are off and the sending stage is not built yet. Changing an assumption does update config/assumptions.json, so change it back afterwards, or note the change.

Questions people ask

Does Ferry send anything to Temenos today?

No. Today it only prepares: it loads, checks and plans. The sending stage, Crossing, is the next build step. Even then, every environment starts with live calls switched off.

Is it only for one bank?

No. There is nothing bank-specific in the code. Each bank's values (environment addresses, service definitions, roles, source formats) go into settings files.

What if Temenos answers a question differently from our assumption?

We switch that assumption in Settings. Every record and step that relied on it is tagged, so we know exactly which ones to re-check or re-plan. Nothing else is affected.

What happens if a run stops half-way?

Every created item is recorded in the ID register as soon as Temenos confirms it. A rerun skips those and continues with the rest, so nothing is created twice.

Can we undo a migration?

That is Return Crossing, build step 7. It will use Temenos's own delete service, always preview first, and only touch items Ferry itself created.

Where is customer data kept?

On the machine running Ferry, in a local database folder that is excluded from Git. All files in the repository are invented test data.

Why do some of my numbers look different in Excel?

Excel may hide leading zeros when displaying numbers. Ferry reads cells as text, exactly as shown. Format CIF and account columns as Text before typing, as the template's instructions say.

Who can use it?

Today it runs on one laptop for one person at a time. Hosting for a team, with sign-in, is listed as a decision still to make.
