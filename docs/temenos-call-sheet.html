Which core banking systems do the APIs work with?

Must answerEnvironmentA-01

Why it matters

Several APIs read customer and account details from the core system. If a bank's core is not supported, LinkUserToContract cannot be used and every user would have to go through CreateVirtualUser, with all its mandatory fields. That changes the data a bank has to supply.

Evidence

  • DocCreateContract, LinkUserToContract, CreateVirtualUser, CreateApprovalMatrixRule and UpdateUserLimits all list Backend APIs: “PartyMS, T24 User API”.
  • DocLinkUserToContract: “Fetches the data from Core System configuration and adds user to contract.” and “If only 'cif' is sent, user will be created in the digital database.”
  • DocError codes, LinkUserToContract: ERR_10001 “Customer details are not present in T24”.
  • DocPrerequisites: “Customers setup in T24 or Party or the core system used.” This is the only hint that other cores are supported.

Ask

Which core banking systems are supported besides Transact (T24) and Party, and through which integration service? Which APIs call the core at all, and which fields do they fetch?

A good answer includes

  • The supported cores and the adapter or integration service for each.
  • The list of APIs that call the core, and the fields each one reads (name, phone, email, date of birth, national ID).
  • What the APIs do when the core is slow or unavailable.

How Ferry handles it today

A-01Per record: a user with their own customer number is linked through the core; anyone else becomes a virtual user. If the core can't be read, switch A-01 to “always virtual”.

Which release includes these APIs, and how is the legal entity chosen?

Must answerEnvironment

Why it matters

A migration tool should use the exception log, the reconciliation report and DeleteMigratedData rather than rebuilding them. They are labelled “New”, so we need to know which releases have them. Every main API also needs legalEntityId.

Evidence

  • Doc“Starting 202510, the following Fabric runtime configurations have been introduced”: SKIP_MIGRATION_NOTIFICATIONS (default true) and DATAMIGRATION_EMAIL_OPTIONAL (default false).
  • DocGetMigrationReconReport, GetMigrationExceptions and DeleteMigrationExceptions are marked “New / Modified: New”, with examples dated April 2026. Exceptions go to a new migration_exception_log table in the dbxlogs database.
  • DocThe document joins two parts with different dates: the Customer Management part (27 Jul 2026) and the Migration API Guide (9 Jan 2025).
  • PostmanlegalEntityId is sent on CreateContract, LinkUserToContract, CreateVirtualUser, limits and payees. All samples use GB0010001. Doc error ERR_22232: “LegalEntityId cannot be null”.

Ask

From which Temenos Digital release are the DataMigration app, the three new APIs and both runtime settings available? How does a bank find its legal entity ID, and can one migration cover several legal entities?

A good answer includes

  • The first release with each piece, and any patch required.
  • Where the legal entity ID is configured, and how multi-entity banks should send it.
  • Who sets the two Fabric properties, and whether the dbxlogs database is always present.

How Ferry handles it today

ConfigLegal entity comes from the row, or from the environment's default in environments.json. A record with neither is blocked (check XR_LEGAL_ENTITY).

How does groupRule say “any 2 approvals from the same group”?

Must answerApproval rulesA-02

Why it matters

Business customers often need “any 2 of the approvers in group A”. If the format is misread, a rule like that becomes “all of A, B and C”, and payments that should go through get stuck. We need the confirmed format before converting any group-based rule.

Evidence

  • DocCreateApprovalMatrixRule reference: groupList holds 2 group IDs and groupRule is "[[0],[2]]".
  • DocSME use case, Step 7: groupList holds 4 group IDs and groupRule is "[[0,1,0,0],[1,0,0,0]]", one 1/0 flag per group.
  • DocParameter table: “Each list with in ‘groupRule’ is AND condition and between the list is OR condition” and “Each ‘groupRule’ list count should not exceed the total count of ‘groupList’ list.”
  • FieldIn an existing Temenos Digital installation, signatorygroupmatrix rows store groupRule '[[1]]', the 1/0 style.

Ask

Which example is correct? Is each number in a row a 1/0 flag, or the number of approvals needed from that group? How do we send “2 approvals from group A” and “1 from A and 2 from B”?

A good answer includes

  • A corrected sample payload for each of those two cases.
  • Whether a count above 1 is supported at all.
  • What happens when the count is larger than the group's member count.

How Ferry handles it today

A-021/0 flag per group. Rules that need more than one approval from the same group are parked for review. Switch to “count per group” if Temenos confirms counts.

4

Do neighbouring amount brackets share a boundary?

Must answerApproval rulesA-03

Why it matters

Every converted approval rule is split into amount brackets. Legacy systems usually write them as 0–1,000 then 1,001–3,000. If the API treats the lower limit as exclusive, an amount such as 1,000.50 falls under no rule at all.

Evidence

  • DocCreateApprovalMatrixRule: brackets "-1.00"→"5", then "5"→"-1.00". The boundary value is reused.
  • PostmanCreateApprovalMatrixRule: "-1.00"→"10", then "10"→"-1.00".
  • DocError ERR_87114 “Approval Rule Initialization Failed - invalid values for limit ranges!”
  • FieldApproval rules exported from legacy systems commonly use the previous upper limit + 1 as the next lower limit.

Ask

Is lowerlimit exclusive and upperlimit inclusive? Must brackets meet exactly (5 then 5)? Does a gap of 1 raise ERR_87114 or leave amounts uncovered? How are decimals handled?

A good answer includes

  • The exact rule, shown with the amounts 1,000, 1,000.50 and 1,001.
  • Confirmation that -1.00 means “open” at either end.

How Ferry handles it today

A-03Neighbouring brackets share the boundary value, as in the vendor examples. Switch to “previous upper + 1” if Temenos says otherwise.

What makes two contracts clash on name, and are retries safe?

Must answerContractsA-07

Why it matters

CreateContract takes no name, yet it can fail with “contract already existing with given name”. Customers often share the same full name. If the contract name comes from the customer's name, many valid contracts would be rejected. It also decides whether a timed-out call can be retried safely.

Evidence

  • PostmanCreateContract saved response: dbpErrCode 21967, FailureReason “[ErrorCode=10401, Message=A contract is already existing with given name, please choose another]”, with opstatus 0.
  • DocThe CreateContract request has no name field. ERR_10401 appears again under UpdateContractLimits: “Contract exists with given name”.
  • FieldThe same 21967 error was returned on real contract creation in an earlier Temenos Digital migration.

Ask

How is the contract name built, must it be unique, and can we pass our own? If a call times out, how do we find out whether the contract was created before we retry?

A good answer includes

  • The naming rule and the scope of uniqueness.
  • A lookup by customer number, or an idempotent retry path.

How Ferry handles it today

A-07A name clash is reported as its own outcome and never retried automatically. The ID register stops a rerun from creating a contract twice.

Which users go through LinkUserToContract and which through CreateVirtualUser? Which fields may be blank?

ImportantUsersA-01A-08

Why it matters

Business users such as a company's accountant often have no customer number of their own. CreateVirtualUser marks every personal field as mandatory, and source data commonly has gaps in email, middle name and tax ID.

Evidence

  • DocCreateVirtualUser: email, phone, phoneCountryCode, firstName, lastName, dob, taxId and middleName are all “Mandatory”. Errors include ERR_10050 “Invalid middle name” and “Invalid ssn”.
  • DocDATAMIGRATION_EMAIL_OPTIONAL (default false) covers email only.
  • DocSME use case: a virtual user is for a “business user who is not a customer of the bank”.
  • FieldLegacy user exports often carry only the company's primary customer number, not one per user, and leave middle name empty.

Ask

For a business user with no customer number of their own, is CreateVirtualUser the route? Can middleName and taxId be empty? Should a national ID number go in taxId? What formats do phone and dob follow?

A good answer includes

  • A decision rule for each user type.
  • The true minimum set of mandatory fields.
  • Field formats and validation rules.

How Ferry handles it today

A-08Users are linked or virtual per record (A-01). A virtual user missing any field the vendor marks mandatory is blocked until it is filled. Switch A-08 to “send blank” if Temenos relaxes the rule.

How do migrated users keep their login name and password?

ImportantUsers

Why it matters

Customers expect to log in with their existing details after migration. The APIs accept a legacy user name but don't mention passwords at all.

Evidence

  • DocLinkUserToContract and CreateVirtualUser: legacyUserName “specifies the userName to be taken for the customer”.
  • Doc“The Implementation team needs to implement onboarding / adding the user into the third-party authentication systems like HID or Uniken separately. This will not be part of the Migration APIs.”
  • FieldA common approach keeps the old password: at first login the password is checked against the legacy system, then stored in the new platform.

Ask

If legacyUserName is the old login name, what does the user type at first login? Is a first-login check against the legacy system supported for users created by these APIs? Are user names checked for format and uniqueness?

A good answer includes

  • The end-to-end first-login sequence for a migrated user.
  • User-name rules and what happens on a duplicate.

How Ferry handles it today

ConfigSends legacyUserName from the source's “Legacy User Name” column and warns on characters the target may refuse. Passwords are outside Ferry.

How do we send amount ranges that need no approval?

ImportantApproval rulesA-04

Why it matters

Many approval rules only start above a threshold, so the range below it needs no approval. Postman shows a form for this that the document never mentions, and its saved response is an error.

Evidence

  • PostmanCreateApprovalMatrixRule body: "isGroupMatrix": "0", and the first bracket "-1.00"→"10" has "approvalruleId": "NO_APPROVAL", "approvers": [], "numberOfApprovals": 0.
  • PostmanSaved response: dbpErrCode 10205, FailureReason “[ErrorCode=87115, Message=Given Limit values are not applicable for the Approval mode!]”.
  • DocNo approvalruleId, isGroupMatrix or NO_APPROVAL in any parameter table. numberOfApprovals “cannot exceed the list of ‘approvers’”.

Ask

Is NO_APPROVAL the supported way to express a range with no approval? What do isGroupMatrix and approvalruleId do, and what caused 87115 here? Or should those ranges simply be left out?

A good answer includes

  • A working sample for “0–1,000 no approval; above 1,000 any 1 of A, B”, in both user and group mode.

How Ferry handles it today

A-04Ranges that need no approval are not sent. Switch to “send as NO_APPROVAL” if Temenos confirms that form.

How many CreateApprovalMatrixRule calls does one legacy rule become?

ImportantApproval rulesA-05A-06

Why it matters

Legacy approval rules often apply to all transaction types at once, and some apply to requests that move no money, such as statement requests. The API takes one action and one limit type per call, so this decides the call volume and the payload for those requests.

Evidence

  • DocactionId Mandatory, “configured in Digital system for a feature”. limitTypeId Mandatory. ERR_10205 “Missing limitTypeId in request”. Every sample uses MAX_TRANSACTION_LIMIT.
  • PostmanGetMigrationReconReport description, SME service definition: “approvalActionsPerCif = 78”.
  • FieldLegacy rule exports commonly use a wildcard (*) for all transaction types, and list non-monetary request codes with amounts of 0–0.

Ask

For an “all transactions” rule, do we call once per approval-enabled action (78?) and once per limit type (transaction, daily, weekly)? For actions that move no money, which limitTypeId and limits do we send?

A good answer includes

  • How to get the approval-enabled action list for a bank's service definitions.
  • The limit types required.
  • A sample for an action that moves no money.

How Ferry handles it today

A-05/06An “all transactions” rule becomes one call per action in the list configured for the contract's service definition (A-05). Rules for actions that move no money are parked for review (A-06).

What does DeleteMigratedData remove for each migration API?

ImportantUn-enrollmentA-12

Why it matters

Re-running a customer cleanly needs everything the migration created to be removed first. Deleting at database level is error-prone: tables such as backendidentifier and customeraction stop a customer from being deleted. We would rather use the product API, but the material documents only one case.

Evidence

  • DocDeleteMigratedData takes apis, contractId, customerId and cif. The only sample sends "apis": ["CreateVirtualUser"] with a contractId and customerId and an empty cif.
  • DocThe sample response lists 12 customer tables and 369 rows: customer, customerlegalentity, customerpreference, customercommunication, customeraccounts, excludedcustomeraccounts, backendidentifier, customergroup, contractcustomers, customeraction (357 rows), customerlimitgrouplimits and customeraddress.
  • DocNo table list or sample for CreateContract, LinkUserToContract, CreateSignatoryGroup, UpdateApprovalMatrixMode, CreateApprovalMatrixRule, limits or payees. Contract-level tables such as contract and contractcorecustomers never appear.
  • PostmanThe same single CreateVirtualUser sample, described as “Destructive — use with caution. Specify apis to limit deletion scope”.
  • FieldA database-level un-enrollment built for an earlier migration needed 93 delete steps to remove a full contract. Real data also contains contracts shared by several customer numbers.

Ask

Which values does apis accept, and which tables does each one delete? Can one call remove a whole business contract with its users, signatory groups, approval rules, limits and payees, and in what order should apis be listed? Which of contractId, customerId and cif are required for each API? How does it handle a contract shared by several customers, or a user on several contracts?

A good answer includes

  • The table list per API.
  • A sample request and response that removes a full business contract.
  • The identifier rules, and the behaviour on shared contracts and shared users.

How Ferry handles it today

A-12Return Crossing (build step 7) will call DeleteMigratedData, limited to IDs in Ferry's ID register. What it can promise depends on this answer.

Is DeleteMigratedData only for failed migrations, or a full un-enrollment?

ImportantUn-enrollmentA-12

Why it matters

Projects need to un-enroll customers who migrated successfully: to repeat test runs, and to back out a customer after cut-over if something is wrong. Many banks also hold customers enrolled earlier by bulk loads or other channels, which never went through these APIs. If the API only cleans up failures, each project needs its own un-enrollment for every other case.

Evidence

  • DocDescription: “This API deletes migrated error data from the database.” Functionality: “Deletes the migrated error data from the database.”
  • Doc“Failed records can be remediated by using the existing rollback API and re-running the migration APIs for the affected records.” The rollback API is not named anywhere else.
  • FieldIn a database-level un-enrollment of a real customer, one interbankfundtransfers row created after enrolment blocked deleting the customer through its foreign key.
  • FieldEarlier migrations often loaded customers by bulk insert or stored procedures, outside these APIs.

Ask

Can DeleteMigratedData remove a customer whose migration succeeded? Does it work for customers created outside these APIs (bulk loads, Spotlight or branch onboarding)? If the customer has logged in and created payments, alerts or messages since migration, are those deleted, kept, or does the call fail? Is “the existing rollback API” this API or a different one?

A good answer includes

  • A clear statement of which customers it may be used on.
  • Its behaviour when the customer has activity after migration.
  • The name and documentation of the rollback API, if it is a different one.

How Ferry handles it today

A-12By design, Return Crossing only removes what Ferry itself created. Customers created any other way are out of its scope.

Is a delete all-or-nothing, can we preview it, and is it logged?

ImportantUn-enrollmentA-12

Why it matters

A delete that stops half-way leaves a customer that can neither log in nor be migrated again. A safe un-enrollment runs as one transaction, shows row counts before anything is deleted, and records who ran it. We need to know what the product API offers before relying on it.

Evidence

  • DocThe response reports a status per table, plus summary: "PASS" and totalDeleted. Nothing says whether the tables are deleted in one transaction, or what a failed table does to the others.
  • DocThere is no preview or dry-run parameter, and no sample of a failed or partial response.
  • DocIts error list is copied from the reconciliation API: ERR_10351 “Failed to generate reconciliation report / stored procedure error”.

Ask

If deleting one table fails, are the earlier deletes rolled back? What do summary values other than PASS look like? Is there a way to get the row counts before deleting? Is each call logged with who ran it and what it removed? Is it allowed in production, and who may call it?

A good answer includes

  • The transaction behaviour, with a sample failure response.
  • A preview option, or confirmation that none exists.
  • Its audit trail and the production policy.

How Ferry handles it today

DesignReturn Crossing will preview from the ID register before calling the API, and record every run in Ferry's audit trail.

How fast can we safely run?

ImportantOperationsA-11

Why it matters

The APIs take one record per call. At one second per call and at least two calls per customer, 100,000 customers need about 2.3 days on a single thread. Running in parallel is essential, but only at a level the platform can take.

Evidence

  • Doc“These API will take single record at a time”.
  • DocThe sample login token was issued at 1727172416 and expires at 1727173616: a 20-minute lifetime. Postman stores it once in X-Kony-Authorization, but the login response also returns a refresh_token.
  • FieldQuestions on safe concurrency for contract creation have gone unanswered in earlier migrations.

Ask

How many parallel calls are safe, and what response time should we expect? What is the default token lifetime, and should we use the refresh token? Are there rate limits on the DataMigration app?

A good answer includes

  • A concurrency figure backed by a test.
  • The recommended way to keep the token valid.

How Ferry handles it today

A-114 contracts at a time, steps inside a contract in order. Token refresh before expiry is part of Crossing (build step 3).

Already confirmed by the material, so no need to ask

  • User-based rules send approvers plus numberOfApprovals, and -1 means all approvers.
  • "-1.00" marks an open end of an amount bracket.
  • groupList and groupRule are sent as strings, not JSON arrays.
  • A user can be in only one signatory group (ERR_21021), and signatories must already be users on the contract (ERR_21018).
  • Customers get no email or SMS during migration by default (SKIP_MIGRATION_NOTIFICATIONS = true).
  • Failures come back inside the response body, not as HTTP errors.
